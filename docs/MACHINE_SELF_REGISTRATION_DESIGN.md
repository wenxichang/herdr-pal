# 企业微信机器自主注册设计

## 1. 目标

允许企业微信单聊用户通过以下命令自主注册运行 Herdr 的机器：

```text
/reg <machine_id> <source1,source2,...>
```

例如：

```text
/reg office-laptop 192.168.0.1
/reg office-laptop 192.168.0.1,10.0.0.0/24
```

注册结果按用户现有机器记录区分：

- 用户没有任何凭据和待审批申请时，首台机器自动签发可用 Key，并通过当前企业微信请求返回。
- 用户已有任意凭据或待审批申请时，新机器进入待审批队列；管理员在 Web 管理后台批准后签发 Key，并主动发送给对应企业微信用户。

本功能只修改 Server，不修改 Pal、HPRP、安装包格式或客户端配置。

## 2. 固定规则

- 只在现有 Web 管理后台提供审批入口，不扩展 HPAP 和 `hp-cli`。
- `/reg` 在用户没有在线 Agent 会话时仍可使用。
- 机器标识继续使用 HPRP 的 `machine_id` 校验规则。
- 来源地址按逗号拆分，复用现有单 IP、CIDR 和同地址族闭区间规则。
- 当前命令只接受机器标识和来源列表两个参数；多余参数明确拒绝，为后续扩展保留空间。
- 同一用户和机器已有凭据时直接拒绝，不执行换 Key、覆盖或来源变更。
- 同一用户和机器已有待审批申请时幂等返回原申请状态，不修改来源规则。
- 启用、禁用和过期凭据都属于已有机器记录。
- 任意待审批申请也属于已有机器记录。
- 被拒绝的申请不保留在本地文件中；如果该用户之后没有凭据和待审批申请，再次注册可重新按首台机器处理。
- Relay URL 继续由管理员直接写入实时读取的 `help.md`，不恢复 `addr_hint` 或新增 URL 配置。

## 3. 架构

新增 `internal/machinereg`，作为机器自主注册、待审批队列和凭据签发之间的独立业务边界。

### 3.1 RegistrationStore

`RegistrationStore` 只保存尚未入库的待审批项目，默认文件为：

```text
<state_dir>/registrations.json
```

文件使用版本化 JSON，目录权限为 `0700`，文件权限为 `0600`。写入采用同目录临时文件、同步和原子替换，与现有 CredentialStore 的持久化策略一致。

待审批记录包含：

```text
registration_id
principal_id
machine_id
allowed_sources
requested_at
```

`registration_id` 使用 `reg_` 前缀加 128 位安全随机数的 Base64URL 编码，生成时检查当前待审批集合避免冲突。它只定位当前待审批项目，不作为永久业务或审计身份。批准或拒绝完成后立即删除记录，不在本地保存审批历史。

### 3.2 MachineRegistrationService

`MachineRegistrationService` 协调 RegistrationStore 与 CredentialStore，负责：

- 首台机器判断和自动签发。
- 创建、查询、批准和拒绝待审批项目。
- 同名凭据与重复申请检查。
- Key 交付失败后的凭据回滚。
- 注册和审批审计事件。
- 同一用户注册操作的串行化。

现有 Web、自动化 API 和 HPAP 的人工凭据签发也应通过同一个协调器，避免管理员签发与 `/reg` 并发时，多个请求同时被识别为首台机器。查询、启禁用、删除和来源变更继续复用现有 CredentialStore 规则。

### 3.3 ConversationRouter

ConversationRouter 增加 `/reg` 解析和执行能力。无会话门禁应放行 `/reg` 与 `/help`，其他命令保持现有行为。

Router 只负责企业微信命令语义、请求级回复和安全提示；首台判断、持久化、签发与回滚由 MachineRegistrationService 完成。

### 3.4 AdminService 与 WebAdmin

AdminService 增加待审批查询、批准和拒绝方法。WebAdmin 增加独立“注册审批”页面和以下接口：

```text
GET  /admin/api/v1/registrations
POST /admin/api/v1/registrations/{id}/approve
POST /admin/api/v1/registrations/{id}/reject
```

接口继续使用现有管理员 Session、同源检查、CSRF、HTTPS 和结构化 HTTP 操作日志。审批 Key 不返回浏览器，只发送给申请所属的企业微信用户。

## 4. 数据流

### 4.1 命令解析与校验

`/reg` 必须包含三个空格分隔字段：命令、机器标识和逗号分隔的来源列表。来源项逐个去除首尾空白，空项、非法规则和空结果都明确拒绝。

校验顺序：

1. 校验命令参数数量。
2. 校验 `machine_id`。
3. 拆分、规范化、去重并稳定排序来源规则。
4. 检查同一用户和机器是否已有凭据。
5. 检查是否已有同一机器的待审批申请。
6. 判断该用户是否完全没有凭据和待审批申请。

### 4.2 首台机器自动签发

当用户没有任何凭据和待审批申请时：

1. CredentialStore 生成并持久化 Key 摘要。
2. Router 通过当前企业微信请求返回一次明文 Key。
3. 回复提示用户发送 `/help` 查看下载和安装步骤。
4. 回复成功后记录 `auto_issue/delivered` 审计事件。
5. 回复失败时删除刚签发的凭据，并记录交付失败和回滚结果。

自动签发不写 `registrations.json`。

### 4.3 创建待审批申请

当用户已有任意凭据或待审批申请时：

1. 持久化新的待审批记录。
2. 通过当前企业微信请求返回申请编号和等待审批提示。
3. 记录 `request/pending` 审计事件。

同一用户和机器已有待审批记录时，返回现有申请编号，不生成新记录，也不修改原来源规则。

### 4.4 管理员批准

管理员在 Web 管理后台确认批准后：

1. 重新读取待审批记录并校验其仍然存在。
2. 重新检查同一用户和机器没有凭据。
3. 签发并持久化新的机器凭据。
4. 使用企业微信主动消息把 Key、机器标识和 `/help` 提示发送给用户。
5. 发送成功后删除待审批记录。
6. 记录管理员、申请、凭据和来源信息的 `approve/delivered` 审计事件。

浏览器成功响应只包含申请结果和 `credential_id`，不包含机器 Key。

如果企业微信发送失败，服务立即删除刚签发的凭据。删除成功后保留待审批记录，管理员可以重试；删除失败时保留申请并返回明确的关联 `credential_id`，阻止盲目重复批准，要求管理员先处理异常凭据。

如果 Key 已成功发送，但删除待审批记录失败，凭据保持可用，后台返回“交付成功但申请清理失败”和关联 `credential_id`。管理员修复存储问题后应删除该异常凭据并重新批准；用户可能已经收到的旧 Key 会随凭据删除而失效。该边界无法在不持久化明文 Key 的前提下与企业微信投递组成原子事务。

### 4.5 管理员拒绝

管理员拒绝时可以填写原因：

1. 删除待审批记录。
2. 主动通知企业微信用户申请已拒绝，并在有值时附带原因。
3. 记录 `reject/rejected` 审计事件。

拒绝通知失败不恢复待审批记录，也不改变管理员决定；服务记录结构化错误日志和审计投递结果。

## 5. 一致性和异常处理

- 同一用户的自主注册、批准和人工签发通过共享协调器串行处理。
- CredentialStore 继续以 `(principal_id, machine_id)` 唯一约束作为最终防线。
- 所有错误必须返回安全、明确的用户或管理员提示，并在运行日志中包含阶段、用户摘要、机器标识摘要、申请编号和安全错误类型。
- 普通日志、注册文件和 Loki 审计不得包含机器 Key。
- Key 只在签发调用栈内短暂存在，并通过企业微信交付一次。
- 企业微信交付失败后删除凭据，以避免“凭据存在但用户没有 Key”的常规死记录。
- 进程可能在凭据持久化与 Key 交付之间的极小窗口崩溃。重启后如果待审批申请与同名凭据同时存在，批准操作应识别为异常冲突并提示管理员删除异常凭据后重试，不恢复或重新生成旧 Key。
- Loki/OTLP 审计继续 fail-open；审计不可用不能阻止注册、批准或拒绝。

## 6. 审计

新增业务审计事件：

```text
herdr_pal.machine_registration
```

使用 `action` 和 `outcome` 表示生命周期：

```text
action: request / auto_issue / approve / reject / rollback
outcome: pending / delivered / rejected / delivery_failed / rollback_failed
```

事件至少包含：

- `principal_id`
- `machine_id`
- 申请编号
- 规范化来源规则
- 管理员用户名（审批操作）
- 可选拒绝原因
- 关联 `credential_id`
- 失败阶段与安全错误类型

正文使用不包含 Key 的可检索注册摘要；拒绝原因经过现有 Redactor 处理。`hpk_...` 继续由 Redactor 统一替换，即使未来错误文本意外包含 Key 也不能进入审计输出。

## 7. Web 管理体验

“注册审批”页面展示：

- 申请编号
- 用户 ID
- 机器标识
- 来源地址
- 申请时间
- 批准和拒绝操作

列表使用现有管理页面的分页、刷新和错误显示模式。批准前需要确认；拒绝时允许输入可选原因。批准成功后只展示 `credential_id`，Key 已直接发送给企业微信用户。

管理页面只展示当前待审批项目，不提供本地审批历史。管理员需要查询历史时使用现有 Loki 审计页面，并可按用户、机器、时间范围和关键字过滤。

## 8. 用户提示与文档

- 无会话提示改为引导使用 `/reg <机器标识> <来源地址>` 和 `/help`。
- 默认 `help.md` 增加 `/reg` 命令、首台自动签发和后续机器等待审批的说明。
- Server 不覆盖已存在的 `help.md`；已部署环境由管理员自行加入注册说明和真实 Relay URL。
- README 更新自主注册、审批和安装流程。

## 9. 测试策略

至少覆盖：

- `/reg` 正确语法、参数数量、逗号来源拆分、空项、机器标识和来源规则错误。
- 用户无在线会话时允许 `/reg`，其他会话命令仍被现有门禁拒绝。
- 首台机器自动签发、返回 Key、提示 `/help`，且不产生待审批记录。
- 已有启用、禁用、过期凭据或任意待审批项时创建审批。
- 同名凭据拒绝和重复待审批申请幂等。
- 首台回复失败后的凭据删除，以及删除失败的明确诊断。
- 批准成功、Key 主动发送、删除待审批记录和浏览器不暴露 Key。
- 批准交付失败后的凭据回滚、申请保留、回滚失败和异常同名凭据诊断。
- 拒绝成功、可选原因、通知失败仍完成拒绝。
- 注册文件权限、版本、损坏输入、原子持久化、稳定排序和并发访问。
- 自主注册与 Web、自动化 API、HPAP 人工签发的并发一致性。
- Web 管理认证、同源、CSRF、分页、批准和拒绝接口。
- OTLP 事件名、字段、严重级别、Loki 查询兼容性和 Key 脱敏。
- 完整执行 `./unittest.sh`、`./build.sh`，并对 credential、machinereg、server、webadmin 和集成链路执行竞态测试。

## 10. 非目标

- 不提供自主删除、轮换或修改机器来源规则。
- 不把审批功能加入 `hp-cli`、HPAP 或自动化 Token API。
- 不保存批准、拒绝或 Key 交付历史到本地 JSON。
- 不保证企业微信外部投递与本地文件更新之间的分布式事务。
- 不修改 Pal 或 HPRP 协议。
