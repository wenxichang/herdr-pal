# 企业微信机器注册审批设计

## 1. 目标

在现有 Web 管理审批之外，为 `herdr-pal-server` 增加企业微信机器人内的机器注册审批能力：

- 服务端配置一组企业微信管理员用户 ID。
- 后续机器注册进入 pending 后，按配置顺序轮转通知其中一位管理员。
- 所有配置管理员都可以通过 `/ls-reg` 查看待审批列表。
- 管理员通过 `/apr 1 2 3` 批准申请，通过 `/rej 1 2 3` 驳回申请。
- 数字编号只属于管理员最近一次 `/ls-reg` 的私有快照，执行前必须与当前全局列表复核。

该功能只修改服务端，不修改 Pal、HPRP/1、HPAP/1 或 Herdr。

## 2. 非目标

- 不持久化管理员的列表快照或通知轮转位置。
- 不增加企微审批历史文件；审批生命周期继续写入现有机器注册审计事件。
- 不替换或删除现有 Web 管理审批。
- 不给 `/rej` 增加驳回原因参数。
- 不在通知失败时尝试下一位管理员，避免企业微信响应不确定时产生重复通知。
- 不承诺批量审批的事务性；每个申请仍按现有单项签发、交付和回滚语义处理。

## 3. 配置

在服务端 `wecom` 配置中增加 `registration_admin_ids`：

```json
{
  "wecom": {
    "bot_id": "...",
    "secret": "...",
    "registration_admin_ids": [
      "zhangsan",
      "lisi"
    ]
  }
}
```

配置规则：

- ID 使用企业微信单聊回调中的用户 ID，并进行精确匹配。
- 字段缺失或空数组表示关闭企微审批通知与命令，Web 管理审批继续工作。
- 每个元素会先去除首尾空白；空白 ID 和重复 ID 会使服务端配置加载失败。
- 数组顺序就是新申请通知的轮转顺序。
- 配置变更需要重启服务端生效。

## 4. 模块边界

新增独立的 `RegistrationApprovalCoordinator`，负责：

- 管理员身份判断。
- 新 pending 申请的管理员轮转通知。
- 为每位管理员保存最近一次 `/ls-reg` 的私有编号快照。
- 复核 `/apr`、`/rej` 编号并调用现有机器注册服务。
- 汇总批量操作结果。

`ConversationRouter` 只负责：

- 解析 `/ls-reg`、`/apr`、`/rej`。
- 在无 Agent 会话时仍允许管理员命令进入审批协调器。
- 把协调器返回的文本回复给当前企业微信请求。
- 在普通用户尝试管理员命令时返回权限错误。

`machinereg.Service` 保持现有职责：

- `ListPending` 提供按申请时间和申请 ID 稳定排序的全局快照。
- `Approve` 签发 Key、主动交付给申请人、交付失败回滚凭据并保留申请。
- `Reject` 删除申请并尽力通知申请人。
- 同一 principal 的注册、审批和凭据变更继续使用现有条带锁串行化。

Web 管理台和 `AdminService` 不依赖企业微信私有编号快照，也不通过协调器执行审批。

## 5. 管理员通知轮转

只有 `machinereg.DispositionPending` 表示新建 pending，并触发管理员通知。
`DispositionAlreadyPending` 不重复通知。

协调器在互斥锁内：

1. 读取当前轮转游标。
2. 选择 `registration_admin_ids[cursor]`。
3. 将游标推进到下一位，末尾回到第一位。
4. 释放锁后调用企业微信主动发送接口。

通知内容包括：

```text
有新的机器注册申请：
用户：user-id
机器：office-pc
来源：192.168.1.20
请执行 /ls-reg 查看当前待审批列表。
```

通知投递规则：

- 每个新申请只选择并尝试一位管理员。
- 投递失败不回滚申请、不改变给申请人的成功回复，也不尝试下一位管理员。
- 失败写入明确运行日志，但管理员 ID 只记录摘要，不记录完整 ID。
- 轮转游标已经推进；下一条新申请继续发送给下一位管理员。
- 管理员列表为空时不发送通知。

## 6. `/ls-reg` 私有快照

只有配置管理员可以执行 `/ls-reg`。协调器调用 `ListPending` 取得当前稳定排序的全局列表，
返回内容包含：

- 从 1 开始的临时编号。
- 申请用户 ID。
- 机器标识。
- 来源地址规则。
- UTC 申请时间。

同时，协调器把列表中的 `registration_id` 顺序复制到：

```text
admin_user_id -> []registration_id
```

快照规则：

- 每个管理员拥有独立快照。
- 再次执行 `/ls-reg` 会完整替换该管理员的旧快照。
- 空列表也会保存为空快照，并明确返回当前没有待审批申请。
- 快照只保存在进程内存中，服务端重启后全部清空。
- 私有快照只保存稳定 ID，不复制 Key 或其他敏感数据。

## 7. `/apr` 与 `/rej`

命令格式固定为：

```text
/apr 1 2 3
/rej 1 2 3
```

解析规则：

- 至少提供一个编号。
- 只接受 ASCII 正整数。
- 同一命令中编号不能重复。
- 编号顺序不改变含义；结果按用户输入顺序展示。
- 不支持逗号分隔、范围表达式或驳回原因。

执行前校验：

1. 确认发送者属于配置管理员。
2. 读取并立即清除该管理员最近一次 `/ls-reg` 私有快照。
3. 私有快照不存在时拒绝执行。
4. 每个编号都必须小于或等于私有快照长度。
5. 重新调用 `ListPending` 读取当前全局列表。
6. 对每个所选编号，比较全局列表同一位置与私有快照中的 `registration_id`。
7. 任一所选位置不存在或 ID 不一致时，整批拒绝，不执行任何批准或驳回。

全局列表允许比管理员私有快照更长。新申请按时间追加到列表尾部时，不会使旧编号失效。
其他管理员或 Web 管理员删除条目导致编号移动时，位置复核会拒绝陈旧操作。

通过校验后，协调器先把所选编号解析成稳定 `registration_id`，再依次调用现有服务：

- `/apr` 调用 `Approve`，管理员审计身份使用带企微来源标记的管理员用户 ID。
- `/rej` 调用 `Reject`，驳回原因为空字符串。
- 某一项失败时继续执行其余稳定 ID。
- 每一项独立返回成功或安全的失败原因。
- 如果校验后某项被 Web 或其他管理员抢先处理，该项会返回不存在或冲突，不会改用移动后的数字位置。

无论列表缺失、编号不一致、全部成功或部分失败，响应末尾都提示：

```text
列表快照已失效，请重新执行 /ls-reg 核实当前条目顺序。
```

管理员必须重新 `/ls-reg` 后才能执行下一次 `/apr` 或 `/rej`。

## 8. Router 行为

新增三个服务端动作：

- `serverActionListRegistrations`
- `serverActionApproveRegistrations`
- `serverActionRejectRegistrations`

这些动作属于全局服务端命令：

- 不能带 `/N` 或 `#N` 定向前缀。
- 不依赖当前 Agent 选择。
- 即使当前用户没有任何在线会话，也必须先进行管理员权限判断并正常执行。
- 非管理员得到“无权执行管理员审批命令”，不能通过错误差异读取 pending 内容。
- 命令仍经过企业微信消息 ID 幂等、用户执行队列和现有限速器。
- 用户输入审计继续记录命令正文；机器注册服务继续记录 approve/reject 生命周期。

当 `/reg` 返回新建 pending 时，Router 先回复申请人已经进入审批，再调用协调器发送管理员通知。
管理员通知是尽力而为的后续动作，不能占用或改变申请人的请求响应。

## 9. 并发语义

协调器使用一个短时互斥区保护：

- 轮转游标。
- 管理员私有快照映射。
- 快照的读取并失效操作。

网络发送、Key 签发和申请人通知不能在该互斥锁内执行。

并发安全依赖两层稳定标识：

1. `/ls-reg` 到命令校验之间使用“编号位置 + registration_id”复核，防止陈旧编号指向其他申请。
2. 校验通过后只使用 `registration_id` 调用领域服务，防止批量处理中列表变化导致错批。

批量操作不是全局事务。前一项批准成功、后一项交付失败时，成功项保持生效，失败项按现有
回滚语义保留 pending；最终响应逐项说明结果并要求重新列表。

## 10. 错误与日志

用户可见错误保持可操作且不暴露内部路径：

- 无权限：提示当前用户不是注册审批管理员。
- 无私有快照：提示先执行 `/ls-reg`。
- 编号格式或重复：显示对应命令用法。
- 编号越界或位置不一致：说明列表已经变化，本次未执行。
- 领域操作失败：逐项显示“已被处理”“凭据冲突”“Key 交付失败，申请仍保留”等安全原因。

普通运行日志：

- 管理员和申请人 ID 使用摘要。
- 可以记录申请 ID、机器标识、操作类型、批量数量、结果和错误阶段。
- 不记录机器 Key、Bot Secret 或完整管理员 ID。
- 管理员通知失败必须包含 `error_type` 和 `reason`。

## 11. 测试策略

配置测试：

- 字段缺失和空数组使用空管理员列表。
- 接受多个合法管理员 ID 并保留顺序。
- 拒绝空白 ID、去除空白后重复的 ID 和错误 JSON 类型。

协调器单元测试：

- 新申请按管理员顺序轮转且每次只发送一人。
- 通知失败不尝试下一人，下一申请继续轮转。
- 管理员列表为空时不发送。
- 每位管理员拥有独立 `/ls-reg` 快照。
- 全局列表增长时原有编号仍可使用。
- 所选位置 ID 变化、全局列表缩短、编号越界或快照缺失时整批拒绝。
- 快照在任何审批尝试后失效。
- 批量单项失败后继续处理后续稳定 ID 并汇总结果。
- 两名管理员基于相同列表竞争时，不会把陈旧编号应用到其他申请。

Router 测试：

- 三个命令解析、用法和定向前缀拒绝。
- 非管理员拒绝。
- 没有 Agent 会话的管理员仍能列出和审批。
- 新建 pending 通知一次，already-pending 不通知。
- 管理员通知失败不改变申请人看到的 pending 结果。

集成与回归测试：

- 使用 fake 企业微信和真实本地注册存储覆盖 `/reg -> /ls-reg -> /apr`。
- 覆盖 `/reg -> /ls-reg -> /rej` 和申请人通知。
- 覆盖 Web 审批后企微管理员使用陈旧编号的拒绝路径。
- 运行 `./unittest.sh`、`./build.sh` 以及注册、Router、Server 相关 race 测试。
